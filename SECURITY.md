# Security Policy

## Reporting a vulnerability

If you have found a security issue in Spacepotatis (the codebase or the deployed
instance), please report it privately to the maintainer:

- **Email:** numminen.mikko.petteri@gmail.com
- **Subject prefix:** `[spacepotatis security]`

Include:

1. A description of the issue and where it lives (file path / URL).
2. The smallest reproduction you have — a payload, a curl invocation, a sequence
   of clicks. Even a one-line description is fine if a full repro is hard.
3. The impact you believe it has (data exposure, privilege escalation, denial
   of service, etc.).

Please do **not** open a public GitHub issue, do not file a public PR with the
exploit attached, and do not post the details on social media until a fix has
shipped. The project is small and run by a single maintainer; a private heads-up
is the fastest path to a fix.

### Response expectations

This is a hobby-scale project, not a commercial service — there is no on-call
rotation. Realistic SLAs:

- **Acknowledgement:** within 7 days.
- **Triage + severity assessment:** within 14 days.
- **Fix or mitigation:** depends on severity. Anything in the "anonymous
  internet account takeover / mass data exposure / RCE" class will be
  prioritized over feature work; everything else is best-effort.

If you do not get an acknowledgement within 14 days, please follow up — email
delivery is not 100% reliable.

## Supported versions

Only the version currently deployed at the production URL (and the `master`
branch on GitHub) is supported. There are no LTS branches and no patch backports.
Fixes ship by deploying a new version of `master`.

## Scope

**In scope:**

- Source code in this repository (`src/`, `scripts/`, `db/migrations/`,
  `.github/workflows/`).
- The deployed Vercel instance (production URL listed in the repo description).
- The data persisted in the project's Neon Postgres database (player saves,
  leaderboard, audit log).

**Out of scope (report upstream instead):**

- Vulnerabilities in third-party services we use:
  - **Vercel** (host) — report at https://vercel.com/security.
  - **Neon** (Postgres database) — report at https://neon.tech/docs/security.
  - **Google OAuth** — report at https://www.google.com/about/appsecurity/.
  - **`next-auth` / Auth.js** — report at https://github.com/nextauthjs/next-auth/security.
  - **`next` / Next.js** — report at https://github.com/vercel/next.js/security.
- Vulnerabilities in any npm dependency we transitively use. If exploitation
  requires a code path we currently use, that's in scope; if it's purely a
  property of the upstream package, please report it upstream and let us know
  so we can pin/upgrade.
- Self-XSS or social-engineering attacks (asking a user to paste an exploit
  into DevTools).
- Denial of service that requires sustained large-scale traffic (e.g. classic
  L7 floods). The Vercel platform absorbs that surface; rate-limiting is
  tracked as an open finding (SEC-002) and is being designed.
- Reports generated by automated scanners that do not include a working
  repro against the deployed instance — please verify before reporting.

## Disclosure

The maintainer handles disclosure simply:

1. You report privately.
2. The maintainer fixes the issue on a private branch and ships it to
   production.
3. Once the fix is live, the corresponding `docs/security/` entry can be
   referenced publicly. Crediting the reporter is welcome — let us know how
   you would like to be credited (or whether you prefer to stay anonymous).

There is no formal bug-bounty program. If a reported issue is genuine and
non-trivial, the maintainer may offer a thank-you message in the project
README; that is the extent of the recognition program.
